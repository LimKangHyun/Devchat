# 일정(캘린더) + 로그인 기기 관리 설계

작성일: 2026-10-28 · 대상: DevChat (`backend/devchat-api`, `frontend`)

이 문서는 두 기능을 다룬다. 서로 독립적이라 **따로 만들고 따로 배포해도 된다.**

- 1부. 일정: DevChat 안의 내 달력, 애플 캘린더 연동, 참여자, 알림, 반복, 채팅 날짜 인식
- 2부. 로그인 기기 관리: 기기별 로그인 목록과 원격 로그아웃

표기: **(사용자 결정)**은 사용자가 대화에서 정한 것이고, **(설계자 판단)**은 대화 중 제안했고 사용자가 반대하지 않은 것 또는 이 문서에서 정한 것이다. 빌더가 바꿔도 되는 것은 **(빌더 재량)**으로 표시했다.

---

# 1부. 일정

## 왜 만드나

팀이 채팅하다가 "다음 주 화요일 3시에 회의해요" 하고 약속을 잡으면 지금은 각자 다른 앱에 옮겨 적어야 한다. DevChat 안에서 바로 일정을 만들고, 같이 할 사람을 넣고, 시간이 되면 알림을 받고, 평소 쓰는 애플 캘린더에서도 보이게 하는 것이 목표다.

## 성공 기준

- 채팅 메시지 속 날짜를 눌러 몇 초 안에 일정을 만들 수 있다.
- 만든 일정이 애플 캘린더의 "DevChat" 달력에 나타나고, DevChat에서 고치거나 지우면 애플 쪽에도 반영된다. 늦어도 애플이 다시 가져갈 때까지.
- 정한 시간(예: 30분 전)에 만든 사람과 참여자 모두 휴대폰 푸시를 받는다.
- 매주 반복 일정(스탠드업 등)이 제대로 반복되고, 한 번만 빼는 것도 된다.

## 하지 않는 것 (처음 범위 밖)

- 애플 캘린더에서 고친 내용을 DevChat으로 가져오기. 구독 방식은 한쪽 방향이다.
- 구글 캘린더 전용 연동. 같은 구독 주소를 구글에 넣으면 보이긴 하지만 따로 다듬지 않는다.
- 참석/거절 응답 **(사용자 결정: 초대 수락 없이 바로 추가해야 응답 안 한 사람도 알림을 받는다)**
- 사람마다 다른 알림 시간
- 반복 일정의 "이번만 시간 옮기기", "이후 모두 바꾸기"
- 채팅방 단위 공용 달력 (일정은 사람 단위이고, 참여자로 공유한다)
- "이번 달 말쯤" 같은 애매한 날짜 인식. 나중에 `@AI` 기능이 생기면 다룬다.

## 실패로 보는 것

- 지운 일정이 애플 캘린더에 계속 남는다. **(사용자가 특히 신경 쓴 부분)**
- 알림이 두 번 오거나(서버가 둘일 때) 아예 안 온다.
- 구독 주소만 알면 남의 일정이 보이는데 그 주소를 막을 방법이 없다.
- 참여자로 넣었는데 상대 달력에 안 보인다.

## 기능

### 1. 일정 데이터

일정 하나에 들어가는 것:

- 제목(필수), 시작·끝 시각 또는 하루 종일, 장소·메모(선택)
- 알림: 여러 개. "N분/시간/일 전" 형태 (예: 30분 전, 하루 전)
- 반복: 안 함 / 매일 / 매주(요일 여러 개) / 매달(같은 날짜) / 매년
  - 끝: 계속 / 특정 날짜까지 / N번
  - 31일처럼 그 달에 없는 날짜는 그 달을 건너뛴다 (애플 캘린더와 같음)
- 반복에서 뺀 날짜 목록 ("이번만 빼기")
- 만든 사람, 참여자 목록
- 시간대는 한국 시간(Asia/Seoul) 고정 **(설계자 판단)**

### 2. 권한 **(설계자 판단)**

- 만든 사람만 고치기와 지우기를 할 수 있다.
- 참여자는 보기와 "이 일정에서 나가기"만 할 수 있다. 나가면 그 사람 달력, 구독 주소, 알림에서 빠진다.
- 참여자로 넣을 수 있는 사람: 내 친구 + 나와 같은 채팅방에 있는 사람. 서버에서도 이 조건을 검사한다.
- 일정을 볼 수 있는 사람은 만든 사람과 참여자뿐이다.

### 3. 참여자 추가 **(사용자 결정)**

- 수락 절차 없이 바로 상대 달력에 들어간다.
- 추가되면 "○○님이 '제목' 일정에 추가했어요" 알림이 간다. 앱 안 알림과 푸시 모두.
- 만든 사람이 시간을 바꾸거나 일정을 지우면 참여자에게 알림이 간다. 제목·메모만 바꾼 경우는 보내지 않는다 **(설계자 판단)**.
- 채팅방에서 일정을 만들 때도 참여자 칸은 비워 둔다 **(사용자 결정)**.

### 4. 알림(리마인더)

- 만든 사람이 정한 알림 시간이 만든 사람과 참여자 모두에게 적용된다.
- 기존 알림 경로(`Notification` + `UserNotificationSender` → 웹소켓 + 웹 푸시)를 그대로 쓴다. `NotificationType`에 일정용 타입을 더한다 (예: `SCHEDULE_REMINDER`, `SCHEDULE_ADDED`, `SCHEDULE_CHANGED`, `SCHEDULE_CANCELED`).
- **하루 종일 일정의 알림 (설계자 판단, 애플 캘린더와 같은 방식):** "그날 오전 9시", "하루 전 오전 9시"처럼 **며칠 전 + 시각**으로 정한다. 그래서 알림은 "분 단위 오프셋"만이 아니라 하루 종일 일정용으로 "며칠 전 + 시각"도 저장할 수 있어야 한다. 기본값은 "하루 전 오전 9시"이다.
- 시간이 있는 일정의 알림 기본값은 "30분 전"이다 (설계자 판단).
- 알림을 누르면 그 일정의 자세히 보기가 열린다.
- 애플 캘린더 쪽 알림에 의존하지 않는다. 구독 달력은 애플이 알림을 기본으로 지운다.

**중복·누락을 막아야 하는 조건 (제약)**

- 배포가 블루/그린(`deployment/deploy.sh`)이라 잠깐 서버 두 대가 같이 돈다. 같은 알림을 두 번 보내면 안 된다.
- 서버가 잠깐 멈췄다가 살아나도 그 사이 알림을 놓치면 안 된다. 몇 분 늦게라도 보낸다. 너무 오래된 것(예: 일정 시작 이후)은 보내지 않는다.
- 권장 방식 **(빌더 재량)**: 1분마다 도는 스케줄러가 "보낼 때가 된 (일정, 반복 회차, 알림 시점)"을 계산해서, `(event_id, occurrence_start, reminder_offset)`에 유니크 키가 있는 발송 기록 테이블에 먼저 넣는다. 넣는 데 성공한 서버만 보낸다. 반복 일정은 미리 행을 다 만들지 말고 필요한 구간만 계산한다.
- 스케줄러는 기존 `SchedulingConfig`(`app.scheduling.enabled`)를 따른다.

### 5. 반복 일정 고치기·지우기 **(사용자 결정)**

- 지우기: "이번만 빼기" 또는 "전체 지우기"
- 고치기: 항상 전체에 적용된다. 이번만 다르게 하고 싶으면 "이번만 빼기"를 한 뒤 새 일정을 만든다.

### 6. 애플 캘린더 연동: 구독 달력 **(사용자 결정: 지우면 애플에서도 지워져야 함)**

- 사람마다 비밀 구독 주소가 하나씩 있다. 예: `https://<도메인>/api/calendar/feed/<랜덤 토큰>.ics`
  - nginx는 `/api/`를 백엔드로 보낸다. 실제 경로는 기존 API 규칙에 맞춘다.
- 일정 탭의 "애플 캘린더에 연결" 버튼은 `webcal://` 주소를 연다. 아이폰이나 맥에서 누르면 바로 구독 화면이 뜬다.
  - 주소 복사 버튼도 둔다. 구글 캘린더 등에 직접 넣을 때 쓴다.
- 이 주소는 로그인 없이 열리는 공개 경로라 `SecurityConfig`에서 열어 줘야 한다. 대신 토큰이 곧 열쇠다.
  - 토큰은 추측할 수 없게 충분히 길고 무작위로 만든다.
  - DB에는 원문 대신 해시를 저장한다 **(빌더 재량)**.
  - "주소 새로 만들기"를 누르면 예전 주소는 바로 못 쓰게 된다.
  - 너무 자주 불리지 않게 IP나 토큰 단위 요청 제한을 둔다 **(빌더 재량)**.
- 주소에 담는 내용: 내가 만든 일정 + 내가 참여자인 일정. 반복 규칙과 뺀 날짜도 담는다.
  - 표준 iCalendar 형식으로 쓴다: `RRULE`, `EXDATE`, `Asia/Seoul` 시간대 정의, 일정마다 고정 `UID`, `LAST-MODIFIED`/`SEQUENCE`
  - 지운 일정은 피드에서 빠지면 애플에서도 사라진다.
  - 달력 이름은 "DevChat"으로 한다 (`X-WR-CALNAME`). 다시 가져가는 주기 힌트(`REFRESH-INTERVAL`, `X-PUBLISHED-TTL`)도 넣는다. 다만 실제 주기는 애플이 정한다.
  - 피드에 개인정보가 과하게 들어가지 않게 참여자는 닉네임만 넣는다 **(설계자 판단)**.
- 반영 지연: 애플이 다시 가져갈 때까지 몇 분에서 한 시간 걸린다. 이 점을 연결 화면에 한 줄로 안내한다.

### 7. 화면 **(사용자 결정: 시안 A)**

- **왼쪽 목록:** 채팅, 친구 옆에 **"일정" 탭**을 둔다 (`SideBar.jsx`의 `activeTab`).
  - 다가오는 일정을 오늘, 내일, 이후 순으로 보여 주고, 맨 아래에 "+ 새 일정" 버튼을 둔다.
  - 위쪽에 "애플 캘린더에 연결" 버튼을 둔다.
- **가운데:** 달력을 보여 준다.
  - **월 보기와 주 보기**를 바꿀 수 있고, ◀ 오늘 ▶ 버튼으로 이동한다.
  - 빈 날짜를 누르면 그 날짜로 만들기 창이 열린다.
  - 일정을 누르면 자세히 보기가 열린다. 만든 사람에게는 고치기와 지우기가, 참여자에게는 나가기가 보인다. 반복 일정이면 이번만 빼기와 전체 지우기를 고를 수 있다.
- **만들기·고치기 창:** 제목, 날짜·시간(하루 종일 체크), 장소·메모, 알림(여러 개 추가), 반복, 참여자(친구와 같은 방 사람 검색)
- **휴대폰 (설계자 판단):** 위에 작은 월 달력, 아래에 고른 날의 일정 목록을 보여 준다.
- 시안 파일: 브레인스토밍 때 보여 준 `calendar-layout.html` (임시 폴더). 색과 모양은 앱의 기존 스타일에 맞춘다.

### 8. 채팅에서 일정 만들기 **(사용자 결정)**

- 메시지 안의 날짜 표현에 점선 밑줄이 생긴다. 누르면 "캘린더에 추가"가 뜨고, 그걸 누르면 만들기 창이 날짜·시간이 채워진 채로 열린다.
- 메시지 툴바에도 "일정 만들기"를 넣는다. 날짜가 없는 메시지에서도 쓸 수 있다.
- 알아듣는 표현 (최소):
  - 절대 날짜: `10월 30일`, `11/2`, `2026-11-02`
  - 상대 날짜: `오늘`, `내일`, `모레`, `다음 주 화요일`, `이번 주 금요일`, `금요일`
  - 시간: `오후 3시`, `15시`, `3시 반`, `15:30`. 날짜와 붙어 있으면 같이 쓴다.
- 기준 날짜는 **메시지를 보낸 시각**이다 (한국 시간).
- 시간이 없으면 하루 종일 일정이고, 시간만 있으면 길이는 1시간으로 둔다 **(설계자 판단)**.
- 제목 기본값은 메시지 내용을 한 줄로 줄인 것이고, 고칠 수 있다.
- 코드 블록, 링크 주소, 멘션 안의 숫자는 날짜로 보지 않는다. 오탐보다 놓치는 쪽이 낫다.
- 날짜 인식은 프론트엔드 순수 함수로 만들고 테스트를 붙인다. 서버는 관여하지 않는다.

## 기존 코드와의 접점 (빌더 참고)

- 알림: `domain/notification` (`Notification`, `NotificationType`, `UserNotificationSender`), 웹 푸시: `domain/push`
- 친구: `domain/member/friend` (`GET /friend`), 채팅방 참여자: `domain/chat/chatroom`
- 보안: `global/security/config/SecurityConfig.java`에서 구독 주소 경로만 `permitAll`로 연다.
- 스케줄: `global/config/SchedulingConfig.java`, 다른 작업 예: `NotificationCleanupJob` (`zone = "Asia/Seoul"`)
- DB: Flyway. 현재 마지막 번호는 `V14__add_chat_message_reply_to.sql`(답장 기능 브랜치)이다. 이 기능은 그 다음 번호를 쓴다. 로컬은 Flyway가 꺼져 있어 마이그레이션을 직접 적용한다.
- 프론트: `components/SideBar.jsx`(탭), `components/chatroom/MessageList.jsx`(메시지 툴바, 본문 렌더링), 모달 스타일은 `components/modals/Modals.module.css`

## 빌더에게 맡기는 것

- 테이블 구조, 이름, API 경로와 응답 모양
- 반복 계산 방식. 직접 구현해도 되고 iCal 라이브러리(예: ical4j, biweekly)를 써도 된다.
- 달력 화면 컴포넌트. 직접 만들어도 되고 가벼운 라이브러리를 써도 된다. 무거운 의존성은 피한다.
- 알림 발송 중복 방지의 구체 구현 (위 제약만 지키면 된다)

# 2부. 로그인 기기 관리

## 왜 만드나

어디서 로그인했는지 보고, 잃어버린 휴대폰이나 남의 PC에 남은 로그인을 원격으로 끄기 위해서다.

## 지금 상태 (중요)

- 로그인 정보(리프레시 토큰)가 **회원당 하나만** 저장된다. `auth/entity/AuthToken`의 키가 `memberId`이다.
- 그래서 다른 기기에서 로그인하면 앞 기기의 리프레시 토큰이 덮여서, 앞 기기는 액세스 토큰이 끝나는 **최대 10분 뒤 로그아웃된다.**
- 로그아웃(`LogoutController` → `authTokenService.logout(memberId)`)도 회원 단위다.
- 따라서 기기 관리를 하려면 먼저 **로그인을 기기(세션) 단위로 저장**하도록 바꿔야 한다. 이렇게 바꾸면 여러 기기 동시 로그인도 같이 해결된다.

## 성공 기준

- PC와 휴대폰에 동시에 로그인해도 둘 다 유지된다.
- 설정에서 내 로그인 기기 목록이 보인다. 기기 이름, 처음 로그인 시각, 마지막 사용 시각, "이 기기" 표시가 나온다.
- 다른 기기 하나를 "로그아웃"하면 그 기기는 늦어도 10분 안에, 가능하면 바로 쓸 수 없게 된다.
- "다른 기기 모두 로그아웃"이 된다.
- 이 기능을 배포해도 기존 사용자가 한꺼번에 로그아웃되지 않는다 **(설계자 판단)**.

## 하지 않는 것

- 새 기기 로그인 알림. 나중에 하기 좋은 후보로 남긴다.
- IP로 위치(도시) 보여 주기
- 기기 이름 직접 바꾸기

## 기능 **(전부 설계자 판단, 사용자는 "로그인 기기 관리 좋다"고만 함)**

### 1. 로그인 세션 저장

- 로그인(폼 로그인 `FormSuccessHandler`, 깃허브 로그인 `OAuth2SuccessHandler`)할 때마다 **세션 행을 하나 새로 만든다.**
  - 세션 id, 회원, 리프레시 토큰(암호화 또는 해시), 기기 정보, 처음 로그인 시각, 마지막 사용 시각, 만료 시각, 끊긴 시각을 저장한다.
- 토큰(액세스, 리프레시)에 세션 id를 넣는다.
- 토큰 재발급(`AuthTokenService.refresh`)은 그 세션의 리프레시 토큰만 바꾸고, 마지막 사용 시각을 갱신한다. 지금 있는 재발급 유예 처리(`TokenRefreshCachePort`)는 유지한다.
- 깃허브 액세스 토큰은 지금처럼 회원 단위(`AuthToken`)로 둔다. 세션과 분리한다.
- 재발급할 때 닉네임 같은 회원 정보는 옛 토큰에서 복사하지 말고 DB에서 읽는다. 기기가 여러 개면 닉네임을 바꾼 뒤 다른 기기가 옛 닉네임을 계속 쓰게 되기 때문이다. 지금 `refresh`는 옛 리프레시 토큰의 클레임을 복사한다.
- 기존 토큰(세션 id 없음) 처리: 처음 재발급할 때 지금 `AuthToken`에 저장된 토큰과 맞으면 세션을 하나 만들어 옮긴다. 그래서 배포 때 모두 로그아웃되지 않는다.
- 만료되거나 끊긴 세션은 주기적으로 지운다.
- 2주(리프레시 토큰 수명) 넘게 안 쓴 세션은 목록에 나오지 않는다.

### 2. 기기 이름

- User-Agent로 "Chrome · Windows", "Safari · iPhone", "DevChat 앱 · Android"(PWA 설치본이면) 같은 이름을 만든다.
- 정확하지 않아도 된다. 알아볼 수 있으면 충분하다.
- IP는 저장한다면 마지막 사용 IP만 남기고, 화면에는 보여 주지 않거나 일부만 보여 준다 **(빌더 재량)**.

### 3. 원격 로그아웃

- 특정 세션 끊기: 그 세션을 "끊김"으로 표시해서, 그 세션의 리프레시 토큰을 더 쓸 수 없게 한다.
- 이미 발급된 액세스 토큰(최대 10분)도 막는다. 권장 방식은 끊긴 세션 id를 Redis에 10분 동안 기록하고, `JwtAuthenticationFilter`와 웹소켓 연결(`StompHandler`의 CONNECT)에서 확인하는 것이다.
- 열려 있는 웹소켓: 그 사용자에게 "이 세션 끊김" 신호(`/user/queue/...`)를 보낸다. 해당 기기 앱은 신호를 받으면 스스로 로그아웃 화면으로 간다. 서버에서 직접 연결을 끊을 수 있으면 더 좋다 **(빌더 재량)**.
- 끊을 수 있는 것은 내 세션뿐이다. 남의 세션 id를 넣으면 거절한다.
- "다른 기기 모두 로그아웃": 지금 세션을 뺀 내 세션을 전부 끊는다.
- 일반 로그아웃 버튼은 **지금 기기만** 로그아웃한다. 지금은 회원 전체를 로그아웃한다.
- 비밀번호를 바꾸면 다른 기기 세션을 모두 끊는다.

### 4. 화면

- 프로필 메뉴(헤더)나 마이페이지에 **"로그인 기기"** 항목을 둔다.
- 목록의 각 줄: 기기 이름, "이 기기" 배지, 마지막 사용(예: "3분 전", "어제"), 처음 로그인 날짜, "로그아웃" 버튼(이 기기 줄에는 없음)
- 맨 아래에 "다른 기기 모두 로그아웃" 버튼을 둔다.
- 로그아웃 버튼은 확인 단계를 거친다. 브라우저 `confirm` 말고 앱 모달을 쓴다.
